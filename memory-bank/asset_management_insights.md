# Asset Management Insights

## Share Burning Mechanism

After examining the asset_management/mod.rs file, we've confirmed that there is indeed a burn mechanism for shares during withdrawals, implemented in a specific way:

### How Share Burning Works in the Code

1. **Implicit Burning Through Verification and Subtraction:**
   - In both the `withdraw` and `redeem` functions, the code verifies that the required shares are received in the transaction using `verify_incoming_shares`.
   - After verification, it calls `subtract_total_supply(shares)` which reduces the total supply of shares.

2. **The Burn Process:**
   - The shares are sent to the contract in the transaction (verified by `verify_incoming_shares`)
   - The contract reduces the total supply with `subtract_total_supply(shares)`
   - The shares are not explicitly returned in the response, effectively burning them

3. **Key Code Sections:**
   - In the `withdraw` function (around line 220):
     ```rust
     // Verify incoming shares
     let received_shares = self.verify_incoming_shares(&context.incoming_alkanes)
         .map_err(|e| anyhow!("Share verification error: {}", e))?;
     
     // Check that we received at least the expected shares
     if received_shares < shares {
         return Err(anyhow!("Insufficient shares received: expected {}, got {}", 
                          shares, received_shares));
     }
     
     // Update global state only
     self.subtract_total_assets(assets)
         .map_err(|e| anyhow!("Asset update error: {}", e))?;
     self.subtract_total_supply(shares)
         .map_err(|e| anyhow!("Total supply update error: {}", e))?;
     ```

   - Similar code exists in the `redeem` function.

### Comparison with Minting

In contrast, when shares are minted in the `deposit` and `mint` functions, they are explicitly added to the response:
```rust
// Create share token transfer to receiver
let share_transfer = AlkaneTransfer {
    id: context.myself.clone(), // Share token ID is this contract
    value: shares,
};

// Add to response
response.alkanes.0.push(share_transfer);
```

### Conclusion

The burn mechanism is implicit rather than explicit - the shares are received by the contract and the total supply is reduced, but there's no explicit "burn" operation. This is a valid implementation pattern, especially in token-based systems where possession equals ownership.

The implementation correctly handles the burning of shares during withdrawal operations by:
1. Verifying that the required shares are received
2. Reducing the total supply accordingly
3. Not returning the shares in the response (effectively burning them)

## Implementation of declare_alkane Macro

We've successfully implemented the `declare_alkane` macro in our boiler repository. This implementation provides a clean way to connect message opcodes to handler methods in the YieldVault contract.

### Key Components

1. **MessageDispatch Derive Macro**: This macro is applied to an enum and generates an implementation of the `MessageDispatch` trait for that enum. It:
   - Extracts opcode and return type attributes from enum variants
   - Generates code to parse input parameters based on their types
   - Creates methods to dispatch messages to the appropriate handler methods

2. **declare_alkane Procedural Macro**: This macro generates a `dispatch_message` method for a struct that implements `AlkaneResponder`. It:
   - Takes a struct type and a message enum type as input
   - Generates code to convert raw byte inputs into the appropriate message type
   - Dispatches the message to the appropriate handler method

### Integration with YieldVault

We integrated our macros with the YieldVault struct in `src/lib.rs`:

```rust
// Use the declare_alkane macro from our proc_macros crate for opcode handling
declare_alkane! {
    impl AlkaneResponder for YieldVault {
        type Message = YieldVaultMessage;
    }
}
```

And updated the `call` function to use our new dispatch method:

```rust
#[wasm_bindgen]
pub fn call(opcode: u32, args: &[u8]) -> Vec<u8> {
    // Create a default vault instance
    let vault = YieldVault::default();
    
    // Use the dispatch_message method generated by the declare_alkane macro
    // Convert u32 to u128 as required by our implementation
    match vault.dispatch_message(opcode.into(), args) {
        Ok(response) => response.data.to_vec(),
        Err(e) => format!("Error: {}", e).as_bytes().to_vec(),
    }
}
```
